# Архитектурное решение: локальное рабочее место сделок

ID: `TA3000-TRADE-WORKSPACE-2026-09-30`.
Дата: 2026-09-30. Change surface: `product-plane`. Solution Intent: `target`.
Статус решения: принято для проектирования расширения. Статус реализации: planned.
Основание: согласование пользователем границ модулей, PostgreSQL, LM Studio и
представления «От числа к источнику» в архитектурном обсуждении.

## Контекст

Нужна связная локальная система для личного журнала, расчёта альтернативных
стопов/риска/ГО, технических отчётов и демонстрации пути данных. Рынок и индикаторы
уже принадлежат data/research plane; восстановление их pipeline ведётся отдельно.
Смешение пользовательских фактов, вычислений и AI-выводов в одном Journal
затрудняет исправления, повторные расчёты и проверку источников.

## Принято

1. Три предметных модуля: Calculator, Journal, Review; перед ними — общий Intake.
2. Прикладной слой координирует вызовы. Journal — долговечные записи/версии и read API.
   Он не публикует TradeChanged, не содержит outbox и не инициирует Review.
3. PostgreSQL хранит пользовательские факты, рабочие заявки и завершённые пакеты.
   Delta остаётся источником рынка, экономики и подготовленных факторов.
4. Calculator и Review получают данные через публичные Market/Research APIs.
   Journal не читает Delta. Фронтенд не обращается к хранилищам или модели напрямую.
5. Локальный LLM runtime — LM Studio за заменяемым адаптером. Формат, методика,
   валидация и контроль качества принадлежат TA3000. Конкретная модель открыта.
6. AI Intake извлекает кандидаты полей; Calculator считает детерминированно;
   Review показывает фиксированные факторы/параметры/значения/состояния и ограниченную
   интерпретацию. AI не подменяет исходные числовые факты.
7. Сохранённые расчёты и отчёты закреплены за входами, версиями и временем анализа.
   Новый расчёт создаёт новый пакет; старый результат не меняется при обновлении Delta.
8. Основное представление происхождения — **«От числа к источнику»**:
   значение → методика и входы → подготовленные данные/пользовательская запись → источник.
   «До/после», сравнение версий и карта выводов остаются возможными будущими видами.
9. Один backend, узкие модульные контракты, HTTP/JSON для браузера, долговечные
   статусы запросов. Микросервисы и отдельная graph DB не являются условиями запуска.
10. Уточнение 2026-10-14: все Workspace market-data consumers используют один
    ProductDataAPI facade над публичными Market/Research products. Общие readers
    разрешают catalogue/economics/analysis/evidence; facade не присваивает хранение,
    расчётные формулы или orchestration. Прикладной lineage reader дополнительно
    читает сохранённые evidence roots через публичные Journal/Review API.
11. Execution contract и analysis series/reference — разные идентичности.
    Default контракта привязан к дате/источнику; сохранённый выбор и факты не
    меняются при ролле. Первый data slice — pinned economics + ручные native
    уровни/fixed quantity; CF-факторы допускаются после проверки price-space mapping.

Пункты 10–11 консолидируют
[уточнённый план интеграции](docs/architecture/product-plane/trade-workspace/journal-integration-plan.md).
Связь с core TA3000 показана в
[общей схеме](docs/architecture/trading-advisor-3000.md); критерии проверки —
[архитектурный стандарт](docs/architecture/product-plane/architecture-standard.md).

## Последствия

- Системе нужны структурированные свидетельства: lineage каждого показанного
  результата нельзя достоверно восстановить задним числом по тексту AI или логам.
- Отсутствие данных — явный статус конкретного фактора/сценария. Факты сделок
  и заметки остаются записываемыми без успешного расчёта.
- Общей транзакции PG/Delta/LLM нет. Commit Journal атомарен; запросы и результаты
  остальных этапов согласуются через IDs, версии и повторяемые команды.
- Для воспроизводимости сохраняются использованные значения и методики;
  повторный расчёт EMA требует ещё и истории/прогрева, а не только Delta version.
- Демонстрация использует реальные принятые свидетельства. Макеты/fixtures
  обозначаются явно и не подтверждают физическую готовность продукта.

## Рассмотренные варианты

| Вариант | Решение и причина |
| --- | --- |
| Journal с Intake, расчётами и AI внутри | Разделён: у фактов, вычислений и интерпретации разные жизненные циклы |
| Intake после Calculator | Отклонён: до расчёта нужен нормализованный и уточнённый ввод |
| Journal → события → Review | Исключён из первой версии: запуск — явная команда прикладному слою |
| UI читает Delta или PostgreSQL | Исключён: скрывает модульные границы и дублирует согласование данных в браузере |
| Ollama как обязательный runtime | Не закреплён; выбран LM Studio, общий LLM-порт сохраняется |
| Полный DAG как главный экран демонстрации | Основным выбран обратный путь конкретного результата; структура pipeline доступна через его зависимости |
| Отдельный сервис/БД lineage | Отложен: достаточно ссылок и read-проекции над свидетельствами владельцев |

## Что этим решением не утверждено

Не утверждены grain карточки, правила ролла/повторного входа, полный факторный
профиль, методика стопов и risk sizing, account equity source, политика свежести,
модель и её качество/latency, retention срок и численные SLO. Предложения по DDL,
DTO и URL из пакета требуют schema/fixtures/tests перед реализацией.

Это открытые вопросы расширенного target. Существующий отдельный Journal v1
ограничивает факты одним эпизодом/контрактом/контекстом счёта; повторный вход требует
новой связанной карточки. Q-GRAIN определяет будущее развитие этой модели, а не
разрешает менять текущую v1-семантику без версии и миграции.

Архитектурное ревью 2026-10-15 подтверждает согласованность принятых границ
дизайна. Code review отдельного Journal baseline выявило условия доставки;
они записаны в [приёмке](docs/architecture/product-plane/trade-workspace/delivery-and-validation.md).
Это не приёмка полного расширения или его runtime.

Решение расширяет продуктовую область узким локальным workflow. Оно не отменяет
live-data policy, release gates, границы shell и существующие правила публикации Delta.
